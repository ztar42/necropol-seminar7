Рассказ за одну минуту

Можно сказать почти дословно

«Я взяла „Петербургский некрополь“ 1912 года — словарь погребённых на петербургских кладбищах. Первый том, буквы А–Г, это 13,6 тысячи статей. Текст получен распознаванием (OCR), поэтому в нём много ошибок: знак смерти † превратился в плюс, единицу, букву Т, а „іюля“ — в „поля“.

По схеме семинара я разбила задачу на семь этапов и подробно проработала этап извлечения дат рождения и смерти. Для него составлена серия из пяти промтов, по которым ИИ написал код. В каждом промте есть и задача, и способ проверки.

Первая версия кода находила дату смерти только у трети статей. После частотного анализа ошибок OCR и трёх доработок — у 93,6 %. Для проверки вручную размечено 100 случайных статей. На последних 40, которые не использовались при отладке, точность по дате смерти 95 %, полнота 97 %. Ещё 417 подозрительных статей программа сама отложила на ручную проверку. Дальше нужно поправить границы родственников, восстановить испорченные OCR годы и перейти к этапам „имя“, „статус“, „кладбище“.»

Словарь терминов

OCR
Распознавание текста со скана. Машина «читает» картинку страницы и ошибается: путает похожие знаки († → «+», «8» → «3»), теряет дореформенную «і».
Статья
Одна запись словаря об одном человеке: «Фамилия, Имя Отчество, …, р. дата † дата (кладбище)».
Регулярное выражение
Шаблон для поиска в тексте. Например, «одна-две цифры, пробел, название месяца, пробел, четыре цифры» находит «16 декабря 1782». Так работал код на семинаре: поиск «продал», «продала»… — это тоже регулярное выражение. Шпаргалка по значкам — в разделе «Что происходит в коде».
CSV
Таблица в виде текстового файла: одна строка — одна запись, столбцы разделены запятыми. Открывается в Excel, Google Таблицах, LibreOffice.
Скрипт
Файл с программой (.py), который запускают одной командой. В проекте их шесть, каждый делает одну вещь.
Функция
Именованный кусок программы, который делает одно действие. Например, norm_year «чинит» год: «т852» → 1852.
Покрытие
У какой доли статей программа хоть что-то нашла. Покрытие показывает, насколько программа «смелая», но не говорит, верно ли найденное.
Флаг
Пометка «тут подозрительно». Например, рождение позже смерти. Программа не исправляет такие места сама, а откладывает их человеку.
Эталон
Статьи, где правильный ответ записан вручную. Ответ программы сравнивается с ним (иначе «золотой стандарт»).
Точность
Какая доля найденных программой дат верна. «Точность 95 %» — из 100 выданных дат 95 правильные.
Полнота
Какая доля дат, которые есть в тексте, найдена. «Полнота 97 %» — из 100 дат, что реально есть, найдено 97.
Отложенная выборка
Вторая порция эталона, которую размечают после окончания отладки. Если подгонять программу под проверочные примеры, она «выучит» их, и оценка будет завышена. Отложенная выборка даёт честную цифру. Так проверяют на экзамене задачами, которых не было в тренировочных.
«Своя» часть статьи
Начало статьи — до родственников («Жена:», «Съ …») и до скобки с кладбищем. Только там лежат даты самого человека.

Почему этот источник

  • Похож на семинарский. На семинаре разбирали актовые книги XVIII в.: однотипные записи, которые надо делить по разделителям. Некрополь устроен так же: тысячи записей по одной формуле.
  • Формула есть, но текст грязный. Можно сформулировать правила деления (пункт 1 задания), но сразу они не сработают. Значит, есть что тестировать и дорабатывать (пункт 3).
  • Публичный и проверяемый. Скан и OCR-текст лежат на archive.org, любой может открыть и сверить.
  • Есть исследовательский смысл. Из дат получаются возраст смерти, сезонность (пик в марте, спад в августе), рост числа захоронений по десятилетиям. Это готовые вопросы для домашнего задания 2.
  • Почему даты, а не другой этап. Это самый сложный и самый ценный этап. Через даты видно все проблемы OCR, а итог легко проверить по смыслу: рождение не может быть позже смерти, возраст в тексте должен совпадать с разницей дат.

Решение — конвейер из скриптов. Каждый берёт результат предыдущего и сохраняет свой в папку output. Так устроено и на семинаре: «поиск разделителя → список разделителей → сверка».

Что происходит в коде

Ниже каждый файл разобран по смысловым блокам. Построчно разбираться не нужно: достаточно понимать, что делает каждый блок и зачем он нужен. Код можно открыть в любом текстовом редакторе, например в VS Code или «Блокноте». Строки, которые начинаются с #, и текст в тройных кавычках """…""" — комментарии на русском. Компьютер их пропускает, они написаны для человека.

necropol_dates.py — всё решение одним файлом

Вход: ничего (сам скачает источник)Выход: те же файлы в output/ и цифры проверки на экране

Тот же код, что в папке code/, собранный в один файл: его удобно переслать или показать целиком. Внутри он разделён заголовками на части «ЭТАП 0 — скачивание», «ЭТАП 1 — разбиение на статьи», «ЭТАП 3 — даты» и «ПРОВЕРКА». Каждая часть устроена так, как описано ниже для отдельных файлов. Ручная разметка (100 статей) встроена в конец файла, поэтому ему не нужны другие файлы проекта. Функция main в конце запускает части по порядку.

Зачем два варианта: поэтапные файлы показывают, как решение строилось по схеме семинара (этап за этапом, с наивной версией v1 для сравнения), а один файл удобен, чтобы просто получить результат. Результаты у них совпадают до байта.

download.py — скачивание источника

Вход: ссылка на archive.orgВыход: data/necropol_t1.txt

Самый простой файл. В нём записан адрес OCR-текста на archive.org. Скрипт скачивает файл и проверяет, что внутри действительно словарь: ищет начало первой статьи «Абаза, Аггей». Если сервер вернул страницу ошибки, скрипт честно об этом скажет, а не запишет мусор. Если файл уже скачан, повторно не качает.

segment.py — разбиение на статьи

Вход: data/necropol_t1.txtВыход: output/entries.csv (номер, фамилия, отсылка или нет, текст статьи), segment_report.txt
Блок 1 · настройки

Вверху записано, откуда брать текст и куда класть результат, а также с чего начинается словарь (START_MARKER = "Абаза, Аггей"). Всё, что выше, — предисловие, его программа отрезает.

Блок 2 · шаблон начала статьи 
ENTRY_START = re.compile(r"^[А-ЯЁA-Z][а-яёъьіѣa-z]+(?:-[А-ЯЁа-яёъьіѣ]+)*,\s")

По-русски: «в начале строки — заглавная буква, потом строчные буквы, возможно через дефис („Гюне-фонъ“), потом запятая и пробел». Латинские буквы разрешены, потому что OCR иногда подставляет латинскую «A» вместо русской «А».

Блок 3 · функция is_junk — «это мусор?»

Для каждой строки отвечает «да» или «нет». Мусор — это номер страницы («27»), колонтитул из цифр и черт, длинная «каша» без пробелов вроде «[о иваиасисивнвин…», очень короткие обрывки. Все выброшенные строки сохраняются в отчёт: можно убедиться, что ничего ценного не потеряно.

Блок 4 · абзацы и переносы

Текст режется по пустым строкам на абзацы. Строки абзаца склеиваются в одну, а перенос «Але- ксандро» превращается в «Александро». Правило: буква, дефис, пробел, буква → убрать дефис и пробел.

Блок 5 · границы букв

Программа ищет, где начинается раздел «Б», «В», «Г»: первое место, где пять кандидатов в статьи подряд начинаются с новой буквы. Так одна случайная строка «Гизешаузенъ, …» в середине раздела «В» не переключит раздел раньше времени.

Блок 6 · сборка статей

Главный цикл (for … in … — «для каждого абзаца сделай…»). Абзац становится новой статьёй, если начинается с «Фамилия,» и с буквы своего раздела. Иначе он приклеивается к предыдущей статье: это продолжение после разрыва страницы или строка стихотворной эпитафии вроде «Прохожий, чтя се, сердечно воздохни…».

Блок 7 · функция split_glued — разрезать склейки

Иногда OCR не оставил пустой строки между статьями: «…кладбище). | Бобровъ, Яковъ…». Функция ищет места, где после «).» или после отсылки «— см. Альштремъ.» идёт новая «Фамилия, Имя» на ту же букву, и режет там. Так нашлось 1 363 склейки.

Блок 8 · запись и контроль

Каждая статья записывается строкой в entries.csv. Отсылки вида «Аксенова, Елизавета — см. Анцъ» помечаются отдельно: дат в них нет, и в подсчёты они не идут. Затем контроль: сколько статей на каждую букву и где нарушен алфавитный порядок. Нарушение означает либо ошибку разбиения, либо OCR-ошибку в фамилии («Ансеновъ» вместо «Аксеновъ»). Всё это пишется в segment_report.txt.

dates_v1.py — наивная версия

Вход: entries.csvВыход: output/dates_v1.csv

Около 40 строк. Ищет «р.» + день + правильное название месяца + год и знак «†» или «+» + дата. Так написал бы любой, кто не видел OCR-текста. Файл оставлен как точка отсчёта: он находит дату смерти только у 33,5 % статей, и на этом фоне видно, что дали доработки.

dates_v2.py — итоговая версия, главный файл

Вход: entries.csvВыход: dates.csv (даты), dates_review.csv (на проверку), dates_report.txt (сводка)
Блок 1 · словарь месяцев с учётом ошибок OCR 
I_NOISE = r"[1!|{(тпшгнШТІі'№‘]?"   # во что OCR превратил «і»
7: rf"{I_NOISE}[юо]{{0,2}}ля",       # юля, поля, 1юля, тюля, оля

Для каждого из 12 месяцев — шаблон, который ловит и правильное написание, и все массовые искажения из таблицы выше. Пример для июля по-русски: «необязательный мусорный знак на месте „і“, потом до двух букв „ю“ или „о“, потом „ля“».

Блок 2 · день, год, знаки рождения и смерти
  • День — одна-две цифры. Допускаются «т» и «|» вместо единицы и двойная дата «15/27».
  • Год — четыре знака из цифр, «т» и «з». «17..» тоже допустим: в самом издании так обозначен неразборчивый год.
  • Знак смерти — любой из + † { | Т т ф — -, но не внутри слова: иначе «т» из «октября» станет крестом. Одиночная «1» считается знаком, только если после неё пробел: «1 5 марта» = † 5 марта.
  • Знак рождения — «р.». «рожд.» обычно значит «урождённая» («рожд. Соймонова»), поэтому дата после «рожд.» засчитывается, только если стоит сразу за словом.
  • Вставка (GAP) — до двух слов между знаком и датой: «р. въ Ригѣ 9 апрѣля», «+ убитъ 12 октября».
Блок 3 · граница «своей» части статьи 
SCOPE_END = …  # «(…кладбище», «Жена», «Сынъ», «Надпись», «Съ М. И. …»

Шаблон находит место, где начинаются родственники или место погребения. Скобка считается границей, только если внутри есть слово «кладбище», «лавра», «монастырь», «пустынь», «собор», «церковь» или «село». Скобка вроде «рожд. Дюлу (Бивоча)» — это просто вариант фамилии.

Блок 4 · функции-«починщики»: norm_year, norm_day, norm_month, iso
  • norm_year: «т852» → 1852; 1336 → 1836 (XIV века в издании нет, значит, 3 — это испорченная 8); «17..» → «год неизвестен».
  • norm_day: «т» и «|» → 1; из «15/27» берёт 15; «115» понимает как «знак 1 + день 15».
  • norm_month: по найденному слову («поня») определяет номер месяца (6).
  • iso: собирает дату в формат «ГГГГ-ММ-ДД», который понимает Excel. Если известен только год или год и месяц, записывает столько, сколько известно.
Блок 5 · функция extract — чтение одной статьи

Сердце программы. Для каждой статьи:

  1. отрезает фамилию до первой запятой;
  2. отрезает всё после границы «своей» части (блок 3);
  3. ищет «р.» + дату → рождение;
  4. после рождения ищет знак смерти + дату → смерть;
  5. если знака нет, берёт первую дату без знака и ставит флаг death_without_mark;
  6. сразу после даты смерти ищет возраст («на 45 г.», «63 л.»);
  7. проверяет итог и ставит флаги.
Блок 6 · флаги — механизм контроля
ФлагКогда ставится
birth_year_out_of_rangeгод рождения не между 1700 и 1912
death_year_out_of_rangeто же для смерти
birth_after_deathрождение позже смерти

Блок 7 · main — запуск и сводка

Проходит по всем 13 620 статьям и записывает результат в dates.csv. Статьи с флагами копирует в dates_review.csv. Исключение — статьи, где единственный флаг death_without_mark: обычно это верная дата, просто без креста. Затем считает покрытие, долю полных дат, совпадение возраста и число флагов каждого вида, печатает сводку на экран и в dates_report.txt.

evaluate.py — проверка по эталону

Вход: dates.csv + gold_dates.csv или holdout_dates.csvВыход: цифры и список расхождений на экране

Для каждой статьи эталона берёт ответ программы и сравнивает с ручной разметкой. Если оба пустые, это верно (даты нет, и программа ничего не выдумала). Если совпадают — верно. Иначе — ошибка, и она печатается с комментарием. Значения «?» (сам текст не позволяет установить дату) в подсчёт не идут. В конце печатаются точность и полнота отдельно для рождения и смерти.

Статьи сопоставляются по первым 45 знакам текста, а не по номеру. Номера сдвигаются, когда исправляется разбиение на статьи, и иначе сравнение «поехало» бы.

Файлы с ручной разметкой: data/gold_dates.csv, data/holdout_dates.csv

Таблицы из четырёх столбцов: начало статьи, правильная дата рождения, правильная дата смерти, комментарий («знак † распознан как „1“», «„поня“ = іюня»). Их можно открыть в Excel и проверить глазами: это лучший способ убедиться, что эталону можно доверять.

Промты для модели Haiku

В отчёте есть второй вариант серии промтов (раздел 02·H): для Claude Haiku. Это небольшая, быстрая и дешёвая модель. Если основную серию писать для «сильного программиста», то серию для Haiku — для «аккуратного стажёра»: ему нужно давать маленькие задания с готовыми данными и сразу проверять результат.

Серия проверена на настоящей Haiku. Промты подавались ей по одному в изолированной папке, где не было ни нашего кода, ни отложенной выборки. После каждого шага было видно, как растёт число найденных дат: 4 039 → 5 277 → 10 872 → 11 077. На последнем шаге Haiku сама сверилась с эталоном и исправила случай, который основная версия так и не решила: двойную дату «19 сентября (1 октября) 1864».

Итог на отложенной выборке — тот же, что у основной версии: 95 % точности и 97 % полноты по дате смерти, те же две ошибки. Haiku находит дату смерти у 89,8 % статей против 93,6 %, потому что в её серии нет правила «если знака † нет, взять дату без знака». Код Haiku сохранён без правок в prompts/dates_haiku.py, промты — в prompts/haiku_prompts.md.

Что сказать, если спросят

«Чтобы проверить, что серия промтов работает, а не просто красиво выглядит, я дала её небольшой модели Haiku. Для неё промты пришлось сделать подробнее: готовые списки искажений и тесты в каждом шаге. По этой серии Haiku написала код с той же точностью на независимой проверке. Значит, ценность в постановке задачи и механизмах контроля, а не в „силе“ конкретной модели.»

Почему код написан так

Почему регулярные выражения, а не нейросеть, которая «сама прочитает»? Правила видны и проверяемы: про каждое можно сказать, почему оно есть. Результат воспроизводим: тот же текст всегда даёт тот же ответ. 13 600 статей обрабатываются за секунды и бесплатно. ИИ использовался там, где он силён: писать и чинить код по описанию. Альтернатива: отправить каждую статью в языковую модель. Это дороже, медленнее, ответы могут меняться от запуска к запуску, и каждую ошибку пришлось бы ловить заново.
Почему только стандартная библиотека Python? Ничего не нужно устанавливать: код запускается на любом компьютере с Python. Проверяющий сможет повторить результат.
Почему несколько маленьких скриптов, а не один большой? Каждый этап можно запустить и проверить отдельно. Когда эталон выявил ошибку этапа 1 (склейки статей), исправлялся только segment.py, а этап дат просто перезапускался. Так же устроен алгоритм со слайда 12: «разбить задачу на этапы, описать каждый отдельно».
Почему сначала частотный подсчёт, а не сразу правила? Варианты ошибок не выдуманы, а взяты из корпуса. Видно, какие из них массовые («поля» — 314 раз), а какие единичные. Это тот же приём, что на семинаре со словарём разделителей: собрать реальные варианты и потом искать по ним.
Почему программа помечает подозрительное, а не исправляет? «1992» могло быть и 1892, и 1882. Если исправлять наугад, ошибка спрячется в данных. Флаг оставляет решение историку. Исправляются только однозначные случаи: «т» вместо «1», год 13xx.
Почему оставлена наивная версия dates_v1.py? Это точка отсчёта. Без неё не видно, что дали доработки: 33 % → 93,6 %.
Почему два эталона (60 и 40 статей)? На первых 60 статьях находились ошибки и исправлялся код, поэтому на них программа почти идеальна (98 %). Это завышенная оценка. Последние 40 размечены после окончания правок, и их цифры (95–97 %) честные.
Почему возраст берётся только сразу после даты смерти? Иначе программа брала «на 2 г.» у внучки или «служилъ болѣе 40 лѣтъ», и сверка возраста давала ложные тревоги. После правки совпадение выросло с 81 % до 91 %.

История доработок

Эта история и есть ответ на пункт «протестируйте и отметьте доработку». Каждую ошибку нашёл механизм контроля, а не случайный взгляд.

  1. v1, наивная версия: дата смерти у 33,5 % статей. Причина: правильных «іюля» и «†» в OCR-тексте почти нет.
  2. Итерация 2: шаблоны по частотам ошибок. Покрытие 91,7 %. Флаги показали новые проблемы: возраст не сходится в 19 % случаев, много статей «год есть — смерти нет».
  3. Итерация 3: разбор флагов. Слова между знаком и датой («+ въ Дрезденѣ 1833»), «Февраля» с заглавной, двойные даты «15/27 ноября», возраст родственников. Самая забавная ошибка: буква «т» внутри слова «октября» принималась за знак †. Её выдало падение числа полных дат. 93,3 %.
  4. Эталон из 60 статей выявил ошибку первого этапа: 1 363 статьи были склеены по две-три. Такое бывает: контроль следующего этапа ловит ошибку предыдущего.
  5. Итерация 4: разрезаны склейки, «своя» часть статьи ограничивается только скобкой с кладбищем, «рожд.» понимается как «урождённая». На эталоне 98 % / 98 %.
  6. Итоговая проверка на 40 новых статьях: 95 % / 97 %. Две ошибки оставлены как задачи на доработку, чтобы оценка осталась честной.

Вопросы и ответы

Почему у половины статей нет даты рождения? Это же плохой результат.

В самом справочнике у многих людей дата рождения не указана: на надгробии или в источнике её не было. На эталоне программа нашла все 27 дат рождения, которые там есть, и не выдумала ни одной. 48,8 % отражают содержание источника, а не пропуски программы.

Откуда уверенность, что 95 % — правда?

40 случайных статей (генератор случайных чисел с фиксированным зерном, выборку можно повторить) размечены вручную после окончания всех правок. Программа их «не видела». Выборка небольшая: при 40 статьях реальная точность может быть на несколько процентов выше или ниже. Для оценки этапа этого достаточно.

Что значит «точность 95 % и полнота 97 %» простыми словами?

Из дат, которые программа выдала, 95 % верны. Из дат, которые реально есть в статьях, программа нашла 97 %.

Покажите, где в коде механизм контроля.

В dates_v2.py это две части. Флаги ставятся в конце функции extract: проверки года, порядка дат и возраста. Сводка и файл на проверку создаются в функции main, в блоке с комментарием «Контроль». Третья часть — отдельный скрипт evaluate.py со сверкой по эталону. У этапа 1 свой контроль: число статей по буквам и нарушения алфавита в segment_report.txt.

Что делать с 417 статьями на проверку?

Это 3,4 % корпуса. Часть исправляется вручную за пару часов. Для части можно сделать полуавтоматический проход, как на семинаре со словарём исключений: программа показывает статью, человек вводит верную дату, ответ сохраняется в файл.

Почему 1336 превращается в 1836, а не в 1886 или 1833?

OCR чаще всего путает 8 и 3. Во втором разряде года тройка точно ошибочна: XIV века в издании нет. Поэтому её надёжно заменить на 8. Другие разряды программа не трогает: «1333» станет «1833», хотя могло быть и «1883». Поэтому такие случаи в эталоне помечены «?» и не учитываются.

Почему годы ограничены 1700–1912?

Том издан в 1912 году, а самые ранние погребения в нём — XVIII века. Год вне этого диапазона почти наверняка ошибка OCR («1992», «0099»), и программа ставит флаг.

Вы сами писали код?

Отвечать честно: код сгенерирован ИИ (Claude) по серии промтов, и это прямо указано в декларации. Тема семинара — вайб-кодинг, поэтому оценивается умение поставить задачу, разбить её на этапы, проверить результат и найти ошибки. Это сделано через механизмы контроля, эталон и сравнение итераций. Перед защитой стоит самой прогнать код и проверить 10 статей эталона (см. последний раздел).

Зачем второй вариант промтов для Haiku?

Это проверка самой серии промтов. Если по ней даже небольшая модель пишет код с той же точностью на независимой выборке (95 % / 97 %), значит, задача поставлена хорошо, а контроль работает. Заодно видно, как писать промты для «слабой» модели: короткие шаги, готовые данные, тесты в каждом шаге.

Почему не сделаны остальные этапы (имя, статус, кладбище)?

Задание просит выбрать один этап и довести его до теста. Этапы 0–1 (подготовка и деление на статьи) сделаны, потому что без них этап «Даты» не запустить. Для остальных в таблице алгоритма описаны правила и контроль: это план следующего шага.

Чем этот подход похож на разобранный на семинаре?

Почти один в один. Семинар: поиск разделителя «продал» → словарь вариантов разделителя → проверка охвата файлов → словарь исключений. У нас: поиск знака † → словарь его OCR-вариантов → проверка покрытия и флагов → файл ручной проверки.

Как это можно использовать в исследовании?

Таблица дат даёт возраст смерти (медиана 56 лет по 5 484 статьям с обеими датами), сезонность (максимум в марте, минимум в августе) и динамику захоронений по десятилетиям. Если добавить этапы «статус» и «кладбище», можно сравнивать продолжительность жизни разных сословий и конфессий (православные, лютеранские, католические кладбища).

Слабые места

Лучше назвать их самой, чем ждать вопроса:

  • Эталон размечен с помощью ИИ. Разметку делала та же модель, что писала код, и она не видела ответов программы. Для надёжности нужна независимая проверка человеком хотя бы части статей.
  • Выборки небольшие (60 + 40). Для оценки этапа хватает, для публикации нужно больше.
  • Дата без знака † может быть датой погребения («Погребена 19 сентября 1907»). Такие случаи помечены флагом, но не разделены.
  • Двойные даты (старый/новый стиль) сохраняются только по старому стилю.
  • Страницы с перемешанными колонками (OCR прочитал две колонки как одну) не восстанавливаются, их единицы.
  • Сделан только первый том (А–Г). Остальные три тома устроены так же, но код на них не запускался.
